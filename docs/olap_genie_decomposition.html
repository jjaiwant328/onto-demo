Two Tables, Two Paths

01The decision

What the analysis concludes, up front — the rest of the document is the evidence.

Keep both tables. sales (135 cols) is the curated fact behind today’s metric views — the interactive Genie path for comp / sales / units. The OLAP cube (848 cols) is a governed superset for deep-dive analytics the summary cannot answer (2-year LLY comps, cost decomposition, weather, pro program, delivery, payment). The OLAP is not a replacement to retire, nor something to serve raw to one Genie space.

Serve each through narrow, grain-scoped, MV-backed Genie spaces over shared conformed dimensions, fronted by a Genie One router — never the wide cube directly. Interactive questions ride slim sales metric views; deep-dive questions ride the five OLAP grain-scoped agents.

The 250-user load test justifies neither drastic move. Real peak demand is ~70 users/hr against a 1,200 target, production latency is an order of magnitude better than the test, and the biggest cost day on record was the test itself. The lever is scan reduction (clustering, MVs, VACUUM), then right-sizing the warehouse against the real curve — not swapping in the cube or jumping to XL.

What is redundant — the overlapping TY/LY measures

The cube’s TY_* / LY_* comparative measures (gross sales, COGS, GM, discounts, comp sales, ship…) do the same job the curated sales summary already does. Carrying them into every interactive Genie space would duplicate sales and inflate width for no gain — so interactive comparative questions are served from sales, and the cube’s unique 713 columns are reserved for the deep-dive path.

04Why the raw cube must not be served to Genie

Keeping the cube is right; serving all 848 columns as one Genie space is not. Five concrete failure modes.

1Context / token blowout

848 column descriptions cannot be curated within prompt-matching budget; the knowledge store degrades and Genie loses the plot.

2Column ambiguity → wrong SQL

Near-duplicate families (TY_*/LY_*/LLY_*, cost variants, *_DRVD) make Genie select the wrong column.

3Mixed grain → double counting

Line-level rows carry hundreds of pre-aggregated period measures; a naive SUM over the detail grain is simply wrong.

4No join model

A flat cube gives Genie no dimensional structure to reason with — no conformed store, calendar, product, or customer.

5Scan cost

Every question scans a ~26 TB-class wide table instead of a narrow, purpose-built view.

05Architecture — two serving paths

Each table gets its own set of narrow, MV-backed Genie spaces over shared conformed dimensions, dispatched by one router. Two distinct sets of metric views — do not confuse them.

AInteractive path — over sales

A small set of slim metric views (≈5) over the curated summary handles the everyday comp / sales / units merchandising questions. Metric views cover ~79% of current Genie queries today; the target MV set lifts that to ~93% while cutting scan.

BDeep-dive path — over the OLAP

The cube’s transaction-detail value decomposes into five grain-scoped agents (below), each a narrow metric view for the advanced questions sales cannot answer. Targeted MVs cover the most common advanced patterns.

The supporting structure (both paths)

  • Conformed dimensions — pull the repeated dims out of both tables into shared dim_store, dim_calendar, dim_product, dim_customer_household, referenced by every agent. This is the de-denormalization that keeps each scan narrow and answers consistent.
  • Centralized measures — every formula defined once in ontology/semantic_measures.yaml (base/derived, grain, additivity), so the split cannot reintroduce double counting.
  • Interactive comparatives on sales — TY/LY period comparisons come from the slim summary metric views rather than re-importing the cube’s wide measure sections.
  • Genie One router — a supervisor classifies intent and dispatches interactive questions to the sales spaces and advanced questions to the OLAP agents, composing cross-domain answers over the conformed dims.

Why 4-key clustering dilutes pruning

From validated query analysis (13,822 sales queries with read_bytes), only the first two keys earn their place; the trailing two are almost never filtered on, yet they dilute file co-location for the keys that matter.

Filtering on Class Nbr (53% of queries, resolves through SKU) yields only ~3% scan reduction today (56.1 vs 59.7 GB); a 523-file validation confirmed classes are mixed within time-pruned files. Concentrating on 2 keys is estimated to lift class pruning from 3% to 30–50%.

Action items (advisory — prioritized by impact / risk)

The 340M deleted rows

07Does the load test justify the drastic moves? No

A review of the 2026-09-01 250-user Genie load test against real production demand and cost — the evidence points away from both a cube-swap and an XL warehouse.

What the test actually exercised

The 284-question set ran against metric views across seven domains (edw_data.genbi_templates_0507/0512.{sales, inventory, weather, plan, events, channel}) plus cross-domain combinations, in a GCP POC workspace — not a single OLAP cube, and not the production sales table. Its absolute figures do not transfer to production.

(a) Was it done properly? — partially; not a basis for a 1,200-user decision

!Wrong environment

Ran on an edw_data.genbi_templates POC (GCP), not the prod table / warehouse. The 44 TB scanned, the node ceiling, and the latencies don’t carry over.

!Bottleneck ≠ warehouse queue

Queue ratio 0.079, compute-wait 0.0. 80% of wall time is executing massive scans (~7,000,000 rows read per row produced; spills) — plus Genie API 429 rate-limits, which a bigger warehouse won’t fix.

!Unrealistic load model

250 Locust clients, no think-time, result cache disabled (0% hits) — saturating bots, not humans; inflates load versus reality.

!Under-scoped for the target

Only 250 of 1,200 users tested, with no ramp curve — and ceilings were already hit at 250, so linear extrapolation is invalid.

!Partial, hand-recovered run

Locust exited with an error; 618 client errors were reclassified post-hoc to reach the 90.8% success figure. Defensible, but not a clean run.

!Latency already fails UX

P50 end-to-end 2m 27s, P95 4m 34s at 250 synthetic users — a poor experience regardless of node count, and a red flag for 1,200.

(b) Does it justify replacing sales with the OLAP cube, or going XL?

No — the evidence points the other way. The cost driver is scan volume, not table choice. sales is a summary; the OLAP cube is far larger transaction detail (848 cols, ~26.8 TB scanned) — swapping it in increases bytes scanned and makes the node ceiling worse.

The pain concentrates in the sales domain, which calls for more curation (aggregates, pruning, conformed dims — §06), not consolidation onto a wide cube. The Genie API 429 ceiling is independent of the table. “Go XL” is a vertical band-aid: it lifts the node ceiling but leaves scan amplification, API limits, and 2.5-minute latencies unaddressed, and won’t linearly reach 1,200.

Usage is bursty, from $5/day quiet to a $914/day peak on Sep 1 — which is the load test itself. In other words, the single most expensive day on record was the synthetic test, not real demand.

Note: this warehouse was labelled rc_finance in the metering export, versus pr_finance elsewhere in this analysis — confirm they refer to the same environment before acting on the figures.

A proper scale test

  • Run in the production environment (the prod table / Genie space / warehouse), not a POC.
  • Size concurrency from real Monday usage (~70 peak users/hr), with realistic think-time and result cache enabled.
  • Ramp against the real curve rather than jumping to 250/1,200 with no ramp.
  • Separate the two ceilings — warehouse (scan/exec) vs. Genie API 429 — and address each.
  • Cut scan volume first (clustering, MVs, conformed dims — §06), then right-size the warehouse against the real curve.

08Advantages of the two-path design

The design is not just avoidance of the anti-pattern — it is a stronger platform on its own terms.

✓Higher answer accuracy

Narrow, curated context per space — Genie picks the right table and column, far better than 848 columns in one room.

✓Trustworthy, grain-consistent KPIs

Governed measures in one place; no detail-vs-pre-aggregate double counting. Numbers that reconcile.

✓Faster & cheaper

Slim metric views + conformed dims mean small scans; the interactive path never pays the cube’s ~26 TB tax.

✓Full coverage preserved

Keeping the cube retains the 713 advanced columns — LLY, cost, weather, pro, delivery — for the deep-dive path.

✓Consistency across spaces

Shared conformed dimensions mean the same store, calendar, product, and customer definitions everywhere.

✓Independent iteration & isolation

Each space is tuned, benchmarked, and versioned separately; a change or failure in one doesn’t ripple to the others.

✓No duplication

TY/LY comparatives reuse the curated sales summary rather than re-importing the cube’s wide measure sections.

✓Governed & owned

An Ontos product, contract, and semantic model per space, each mapped to a business domain and owner.

AAppendix — assumptions & next steps

  • Cross-metastore reachability — pr_core_raw_v1 and pr_core_raw likely do not live in the jai_classic_ws metastore; the metric/serving views must be built where the source data is reachable (naming stays jai_ per convention).
  • Column curation — the exact expose-vs-hide set and the lean measure list per space need a DESCRIBE-validated pass on the deployed 848-column table before writing SQL expressions (unqualified/incorrect columns cause runtime “column does not exist”).
  • Fulfillment domain — the Omnichannel agent has no existing entry in the app’s DOMAIN_DEFS; either add one or attach it under merchandise_inventory / sales_pos.
  • Warehouse naming — reconcile rc_finance (metering export) with pr_finance (elsewhere) before quoting cost figures operationally.
  • Suggested next step — produce the per-space column manifest (which of the 848 columns each view exposes or hides) and a benchmark set of ≥5 questions per space for run-and-tune, then execute the §06 tuning on sales.

BAppendix — rebuilding sales from the OLAP

An exploratory aside, separate from the recommendation above — not a dependency of the two-path design.

Could the curated pr_core_raw.default.sales summary be regenerated from the OLAP cube? The OLAP is finer-grained transaction detail that carries all four of sales’s grain keys — SLS_DT, SKU_NBR, STR_NBR, CUST_HH_ID_KEY — so sales is essentially a roll-up of the OLAP to that grain. By column name, 76 of 135 sales columns (56%) have a direct source in the OLAP; the remaining 59 are derived, keyed, or multi-year and need recomputation or other sources.

Illustrative roll-up

-- sales ≈ roll-up of the OLAP detail to the summary grain
SELECT
  SLS_DT, SKU_NBR, STR_NBR, CUST_HH_ID_KEY,
  SUM(TY_SLS_AMT)                  AS TY_SLS_AMT,
  SUM(TY_GROSS_SALES_AMT)          AS TY_GROSS_SALES_AMT,
  SUM(TY_COGS_AMT)                 AS TY_COGS_AMT,
  COUNT(DISTINCT UNIQUE_TRANS_ID)  AS TY_SLS_TXN,        -- count, never SUM
  ANY_VALUE(HH_ID)                 AS HH_ID,             -- grain-constant attribute
  -- derived measures are recomputed from components, not copied:
  SUM(TY_GROSS_SALES_AMT) - SUM(TY_COGS_AMT) AS TY_GM_AMT
FROM pr_core_raw_v1.default.sls_cust_trans_dtl_olap
GROUP BY SLS_DT, SKU_NBR, STR_NBR, CUST_HH_ID_KEY;

Verdict: because the OLAP is finer-grained and transaction-grounded, it is a viable — arguably better — source for regenerating the additive core of sales (~56% direct, plus derived measures recomputed from components). A faithful 1:1 rebuild also needs recomputed GM/retail measures, pipeline-assigned surrogate keys, and multi-year comp logic, so treat the OLAP as a strong basis, not a drop-in replacement — which is exactly why the two-path design keeps both tables.
